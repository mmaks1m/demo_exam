## Аннотация

Настоящий «Регламент обновления прикладного программного обеспечения» устанавливает обязательный порядок подготовки, тестирования, безопасного выпуска, централизованного распространения, установки и отката обновлений компонентов программно-технического комплекса «ShoeShop» («Магазин обуви»). 

Документ регламентирует процедуры сопровождения десктопного клиентского приложения на базе **PySide6 (Qt 6)**, серверных служб взаимодействия, реляционной базы данных **PostgreSQL 14+** (включая скрипты миграций схемы данных и ORM **SQLAlchemy 2.0**), а также изолированных конфигурационных параметров в файлах окружения `.env`.

Нормативной базой регламента являются:
- **ГОСТ Р 58412-2019** («Защита информации. Разработка безопасного программного обеспечения. Управление конфигурацией», п. 5.5.3, 5.3.4);
- **ГОСТ 34.601-90** («Автоматизированные системы. Стадии создания», стадия 7 «Ввод в действие» и стадия 8 «Сопровождение АС»);
- **ГОСТ Р 56939-2024** («Защита информации. Безопасная разработка программного обеспечения. Общие требования»);
- **Методический документ Банка России / ФСТЭК России (2021 г.)** («Профиль защиты прикладного программного обеспечения...», требования ALC_FPU_EXT.1, ALC_LCD_EXT.3, AMA_SIA_EXT.3, FPT_TUD_EXT.1, процесс DevSecOps);
- **ГОСТ 19.508-79** и **ГОСТ 19.202-78** (Единая система программной документации).

## 1. ОБЩИЕ ПОЛОЖЕНИЯ

### 1.1. Назначение и цели документа
Настоящий Регламент является нормативным документом, определяющим единые требования, последовательность выполнения операций, матрицу ответственности и контрольные показатели при выпуске, верификации, развертывании и сопровождении обновлений компонентов программно-технического комплекса автоматизации обувного магазина «ShoeShop» («Магазин обуви»).

Основными целями регламента являются:
1. Обеспечение бесперебойного и непрерывного функционирования торговых точек, кассовых узлов и пунктов выдачи заказов торговой сети в процессе модернизации прикладного ПО;
2. Минимизация рисков сбоев, деградации производительности и нарушения целостности реляционной базы данных PostgreSQL при накатывании изменений;
3. Обеспечение информационной безопасности и доверенности прикладного ПО в соответствии с ГОСТ Р 56939-2024 и требованиями методических документов ФСТЭК России;
4. Исключение несогласованности версий между толстыми клиентами пользователей (менеджеров, кассиров, администраторов) и структурой данных СУБД;
5. Регламентация гарантированного восстановления работоспособности системы (процедура Rollback) при обнаружении критических дефектов с соблюдением нормативов RTO < 15 мин и RPO = 0.

### 1.2. Область применения
Действие настоящего регламента распространяется на следующие составные части ПТК «ShoeShop»:
- **Клиентская часть:** Настольное прикладное приложение оператора/менеджера `ShoeShopApp` (Python 3.11, графический фреймворк PySide6 / Qt 6, автономные исполняемые сборки PyInstaller `.exe`), развернутое на автоматизированных рабочих местах (АРМ) кассиров, продавцов-консультантов, товароведов и администраторов магазинов;
- **Серверная часть:** Фоновые службы интеграции, REST API обмена с внешними системами учета и терминалами сбора данных (FastAPI / Uvicorn), развернутые на сервере приложений под управлением Linux / Windows Server;
- **Уровень хранения данных:** Реляционная СУБД PostgreSQL 14+, включая таблицы сущностей (`users`, `pickup_points`, `items`, `orders`, `orders_items`), хранимые функции, триггеры, индексы и версионируемые скрипты миграций структуры данных (Alembic);
- **Конфигурационный уровень:** Файлы окружения `.env`, строки подключения `DB_URL`, криптографические ключи, сертификаты и параметры логирования.

### 1.3. Нормативная база
Регламент разработан с учетом требований и положений следующих нормативно-технических документов:
- **ГОСТ Р 58412-2019** «Защита информации. Разработка безопасного программного обеспечения. Управление конфигурацией» (п. 5.5.3 «Управление обновлением программного обеспечения», п. 5.3.4 «Прослеживаемость изменений»);
- **ГОСТ 34.601-90** «Информационная технология. Комплекс стандартов на автоматизированные системы. Автоматизированные системы. Стадии создания» (стадия 7 «Ввод в действие», стадия 8 «Сопровождение АС»);
- **ГОСТ Р 56939-2024** «Защита информации. Безопасная разработка программного обеспечения. Общие требования»;
- **Методический документ ФСТЭК России / Банка России (2021 г.)** «Профиль защиты прикладного программного обеспечения автоматизированных систем и приложений» (требования семейств ALC_FPU_EXT.1, ALC_LCD_EXT.3, AMA_SIA_EXT.3, FPT_TUD_EXT.1);
- **ГОСТ 19.508-79** «Единая система программной документации. Руководство по техническому обслуживанию. Требования к содержанию и оформлению»;

## 2. ТЕРМИНЫ И ОПРЕДЕЛЕНИЯ

В настоящем Регламенте применяются следующие термины с соответствующими определениями:

- **Прикладное программное обеспечение (ППО)** — совокупность программных компонентов «ShoeShop», реализующих функции автоматизации учета обувных товаров, оформления заказов, управления скидками и разграничения доступа пользователей.
- **Обновление ПО (Update / Patch / Release)** — санкционированная совокупность изменений в программном коде, конфигурационных файлах или структуре базы данных, предназначенная для устранения ошибок, закрытия уязвимостей или добавления новой функциональности.
- **Семантическое версионирование (Semantic Versioning, SemVer 2.0.0)** — система нумерации версий формата `MAJOR.MINOR.PATCH`, однозначно отражающая степень совместимости изменений с предыдущими релизами.
- **Миграция базы данных (Database Migration)** — версионированный детерминированный программный сценарий (скрипт SQL / Alembic), последовательно переводящий реляционную схему СУБД с версии $N$ на версию $N+1$ (`upgrade()`) либо выполняющий обратное преобразование (`downgrade()`).
- **Технологическое окно обслуживания (Maintenance Window)** — регламентированный интервал времени низкой деловой активности предприятия (ночные часы), в течение которого допускается временная недоступность сервиса для проведения плановых технических работ.
- **Откат обновления (Rollback)** — комплекс процедур по экстренному возврату программного комплекса к предыдущему заведомо стабильному состоянию при обнаружении критических дефектов или сбоев.
- **Контрольная сумма (Hash / Digest)** — уникальное цифровое значение фиксированной длины, рассчитанное по криптографическому алгоритму (SHA-256 / ГОСТ Р 34.11-2012) для проверки подлинности и целостности установочных пакетов.
- **DevSecOps** — методология непрерывной интеграции, доставки и развертывания ПО, объединяющая разработку, обеспечение информационной безопасности и эксплуатацию с автоматизированными проверками статического (SAST) и динамического (DAST) анализа кода.
- **RTO (Recovery Time Objective)** — максимально допустимое время восстановления полной работоспособности ПТК «ShoeShop» после возникновения сбоя при обновлении (норматив: не более 15 минут).
- **RPO (Recovery Point Objective)** — максимально допустимый период потери данных транзакций при сбое (норматив: 0 секунд, нулевая потеря данных).

## 3. ВИДЫ И ПЕРИОДИЧНОСТЬ ОБНОВЛЕНИЙ

### 3.1. Классификация обновлений по Semantic Versioning (SemVer 2.0.0)

Все релизы и патчи программного комплекса «ShoeShop» классифицируются в соответствии с международным стандартом SemVer 2.0.0 (`MAJOR.MINOR.PATCH`):

| Тип обновления | Обозначение SemVer | Периодичность / Срок | Окно обслуживания | Содержание и влияние на комплекс |
| :--- | :---: | :---: | :---: | :--- |
| **Мажорное (Major)** | `X.0.0`<br>(изменение первой цифры) | 1 раз в 6–12 месяцев | Обязательно (План, до 3 ч.) | Кардинальная модернизация архитектуры комплекса, переработка структуры ключевых таблиц БД (`orders`, `items`, `users`), замена фреймворка (например, миграция с Qt 5 на PySide6), несовместимость с предыдущими клиентами. |
| **Минорное (Minor)** | `X.Y.0`<br>(изменение второй цифры) | 1 раз в месяц (по спринтам) | Обязательно (План, до 1 ч.) | Добавление новой бизнес-функциональности без нарушения обратной совместимости (новые отчеты, алгоритмы скидок, интеграция с новыми сканерами ШК, добавление колонок с `DEFAULT`). |
| **Патч / Исправление (Patch)** | `X.Y.Z`<br>(изменение третьей цифры) | 1 раз в 1–2 недели | Кратковременное (до 15 мин) | Устранение некритических ошибок пользовательского интерфейса, оптимизация SQL-запросов, исправление верстки карточек товаров, валидация полей ввода. |
| **Экстренное (Hotfix / Security)** | `X.Y.Z.hotfix` или внеплановый `PATCH` | Немедленно (до 4 ч.) | Экстренное (по согласованию CISO) | Закрытие критических уязвимостей безопасности (CVE/БДУ ФСТЭК), блокировка сбоев кассовых операций, аварийные патчи при обрывах связи с СУБД. |

### 3.2. Регламент окон обслуживания (Maintenance Windows)

1. **Плановые технологические окна:** Выполняются исключительно во вторник или четверг с 23:00 до 02:00 по местному времени, вне часов работы розничных магазинов и пунктов выдачи заказов сети «ShoeShop».
2. **Предварительное оповещение:** За 24 часа до начала планового обновления системный администратор направляет электронное уведомление всем руководителям магазинов, товароведам и кассирам с указанием графика работ.
3. **Блокировка доступа:** За 15 минут до начала работ сервер приложений активирует режим обслуживания (`Maintenance Mode`), запрещающий создание новых сессий в БД и информирующий операторов о необходимости завершения активных транзакций.
4. **Экстренные окна:** Назначаются решением Главного инженера по согласованию с Руководителем службы ИБ в любое время суток с предварительным оповещением персонала за 15 минут до принудительного разрыва сессий.

## 4. ОБНОВЛЕНИЕ КЛИЕНТСКОЙ ЧАСТИ

### 4.1. Обновление десктопного приложения (ShoeShopApp)

Клиентская часть `ShoeShopApp` представляет собой настольное приложение на Python 3.11 / PySide6, скомпилированное в виде автономного дистрибутива под управлением Windows 10/11 x64. Процесс обновления включает следующие этапы:

1. **Сборка и упаковка:** 
   Сборка стабильного релиза осуществляется через сборочный скрипт PyInstaller в защищенном контуре CI/CD. Создается монолитный инсталлятор `ShoeShop_Setup_X.Y.Z.exe`, включающий исполняемый файл, Qt-библиотеки, стили и локализацию.
2. **Контроль целостности по ГОСТ Р 58412-2019 (п. 5.5.3):**
   Для собранного пакета вычисляется контрольная сумма по алгоритму SHA-256 (ГОСТ Р 34.11-2012). Значение хеш-суммы заносится в подписанный реестр обновлений и файл манифеста `version.json`.
3. **Каналы распространения:**
   - *Автоматизированный корпоративный канал:* Распространение дистрибутива через групповые политики Active Directory (GPO) или систему управления конфигурациями (SCCM / Ansible) с ключами «тихой» установки:
     ```powershell
     ShoeShop_Setup_X.Y.Z.exe /VERYSILENT /SUPPRESSMSGBOXES /NORESTART
     ```
   - *Сетевой файловый репозиторий:* Размещение пакета на защищенном файловом сервере компании `\\srv-shoeshop\updates\client\`.
4. **Автоматическая проверка версий в приложении:**
   При каждом запуске `ShoeShopApp` выполняет безопасный запрос к серверной таблице `system_settings` или файлу версий. При наличии критического обновления приложение блокирует интерфейс ввода и выводит информационное окно о необходимости обновления, предотвращая работу с устаревшими моделями данных.

### 4.2. Обновление мобильного приложения и терминалов сбора данных (ТСД)
- Обновление специализированного ПО ТСД (Android Enterprise / CipherLab / Urovo) осуществляется через корпоративную систему мобильного управления (MDM / RuStore Enterprise).
- Установка обновлений производится централизованно в ночное время при нахождении терминалов в зарядных док-станциях с подключением к корпоративной сети Wi-Fi.

## 5. ОБНОВЛЕНИЕ СЕРВЕРНОЙ ЧАСТИ

Серверный уровень комплекса «ShoeShop» включает API-шлюзы обмена данными, фоновые воркеры печати ценников и службы синхронизации складских остатков.

1. **Бесшовная схема развертывания (Blue-Green / Rolling Update):**
   Для обеспечения нулевого простоя (Zero-Downtime Deployment) серверные компоненты разворачиваются в Docker-контейнерах за обратным прокси-сервером Nginx. Новый релиз (Green) запускается параллельно с действующим (Blue), проходит процедуру проверки состояния (`healthcheck`), после чего трафик мгновенно переключается на новый контур.
2. **Управление конфигурациями и переменными окружения (.env):**
   В соответствии с ГОСТ Р 56939-2024 категорически запрещается хранение паролей БД, секретных ключей JWT и токенов интеграции в программном коде или репозитории Git. Конфигурация изолируется в защищенном файле `.env`, права доступа к которому ограничены учетной записью службы (права `0600` в Linux / ACL Администраторы в Windows). При обновлении структуры параметров конфигурации системный инженер создает файл `.env.template` с описанием новых директив.
3. **Мониторинг и логирование:**
   Все системные события, ошибки `HTTP 5xx`, исключения SQLAlchemy и обрывы соединений агрегируются в локальные ротируемые журналы (`shoeshop_server.log`) с обязательным аудитом IP-адресов и учетных записей операторов.

## 6. ОБНОВЛЕНИЕ БАЗЫ ДАННЫХ (МИГРАЦИИ)

База данных комплекса «ShoeShop» функционирует под управлением СУБД PostgreSQL 14+. Структура таблиц `users`, `pickup_points`, `items`, `orders`, `orders_items` версионируется с использованием инструмента миграций **Alembic** и ORM **SQLAlchemy 2.0**.

### 6.1. Регламент разработки и утверждения миграций
1. Любое изменение схемы данных (добавление таблиц, столбцов, внешних ключей, индексов) оформляется в виде изолированного скрипта миграции Alembic, содержащего функции прямого применения `upgrade()` и обратного снятия `downgrade()`.
2. Запрещается вносить изменения в рабочую схему БД вручную через утилиты администрирования (pgAdmin, DBeaver, psql).
3. Скрипт миграции проходит обязательную проверку DBA на тестовой базе (Staging), идентичной промышленной по объему и индексам, для выявления долгих эксклюзивных блокировок таблиц (`ACCESS EXCLUSIVE LOCK`).

### 6.2. Порядок применения миграции на промышленном контуре

```bash
# 1. Фиксация текущей ревизии схемы данных
alembic current

# 2. Создание полного аварийного дампа перед обновлением
pg_dump -U postgres -d shoeshop_db -F c -b -v -f /backup/shoeshop_pre_v1_2_0.dump

# 3. Накатывание миграции до целевой версии в рамках окна обслуживания
alembic upgrade head

# 4. Верификация ревизии и целостности структуры
alembic current
python scripts/verify_db_schema.py
```

### 6.3. Требования к обратной совместимости
При минорных обновлениях миграции базы данных обязаны проектироваться по схеме **Expand and Contract (Разделяй и властвуй)**:
- Этап 1 (Expand): Добавление новых колонок с ограничением `NULL` или значением по умолчанию (`DEFAULT`). Старая версия приложения продолжает работать с базой без ошибок;
- Этап 2: Выпуск и развертывание новой версии клиентского ПО, использующей как старые, так и новые структуры;
- Этап 3 (Contract): Удаление устаревших неиспользуемых колонок в следующем плановом мажорном релизе.

## 8. ОТКАТ ИЗМЕНЕНИЙ (ROLLBACK)

### 8.1. Критерии инициации процедуры отката
Решение об экстренной отмене обновления и откате системы принимается Главным инженером проекта при наступлении хотя бы одного из следующих событий:
1. Ошибка применения миграции базы данных PostgreSQL, повлекшая сбой транзакции или блокировку ключевых таблиц;
2. Сбой приемо-сдаточного тестирования (Smoke Test) на шаге 9: невозможность авторизации пользователей, искажение цен/скидок на обувь, сбой генерации проверочных кодов заказов;
3. Превышение длительности регламентного окна обслуживания более чем на 30 минут без достижения стабильного состояния;
4. Обнаружение критической уязвимости нулевого дня или дефекта целостности данных после запуска комплекса.

### 8.2. Пошаговый алгоритм отката

```
[Обнаружение критического сбоя]
               │
               ▼
[Остановка серверных служб и клиентских сессий]
               │
               ▼
[Восстановление БД: alembic downgrade ИЛИ pg_restore из pre-дампа]
               │
               ▼
[Восстановление предыдущей версии ПО и конфигурационных файлов .env]
               │
               ▼
[Контрольный Smoke-тест восстановленной системы]
               │
               ▼
[Снятие режима обслуживания и уведомление руководства]
```

1. **Остановка компонентов:** Принудительное завершение процессов `ShoeShopApp` на АРМ пользователей, остановка серверных демонов FastAPI/Nginx;
2. **Откат базы данных:**
   - Если сбой изолирован в миграции: выполнение команды `alembic downgrade -1`;
   - Если повреждена структура данных: полное восстановление из предрелизного дампа:
     ```bash
     dropdb -U postgres shoeshop_db
     createdb -U postgres shoeshop_db
     pg_restore -U postgres -d shoeshop_db -v /backup/shoeshop_pre_v1_2_0.dump
     ```
3. **Откат клиентского ПО:** Переключение сетевого репозитория `\\srv-shoeshop\updates\client\` на предыдущий пакет `ShoeShop_Setup_X.Y.(Z-1).exe` и принудительное распространение через GPO;
4. **Контрольная проверка:** Проверка доступности данных каталога и сохранности заказов покупателей;
5. **Составление акта об откате:** Фиксация инцидента в «Журнале учета обновлений» с указанием причин и времени простоя.
